# Realtek RTL8111/8168 driver (the AM4 board's NIC)

Hardware: `08:00.0 10ec:8168`, PCI revision `0x15`, subsystem `1043:8677`, on the PRIME B450M-A II
(`hal/fixtures/ryzen-pci-config.txt`). BAR0 is the I/O-space copy of the registers (`0xf000`, 256 B), **BAR2** the memory
window (64-bit, 4 KiB, `0xf6504000`) the driver maps, BAR4 (16 KiB) is not used. Firmware leaves memory decode, bus mastering
and INTx-disable set. `nic=net` is interrupt-driven (MSI-X via BAR4's table, else MSI, else polled; the 100 Hz `network::tick` is always the backstop); `nic=netpoll` is the polled escape hatch. Interrupts are written but **not yet verified on the board**: check the `rtl8168: MSI-X to vector` line and `NIC interrupts` in `/proc/nic`.

## Status

**Works on the AM4 board (`nic=net`, polled at the time): DHCP lease in 12 s (192.168.100.8/24), ping of the router, DNS, HTTP (577 B), `udp_test` and `icmp_test` PASS.** The fix that made RX work was opening `MISC.RXDV_GATED_EN` (the 8168g/h leaves reset with it closed) and the ERI FIFO setup, `mac_start_8168gh` in `hal/src/rtl8169.rs`. Before it: 7 TX, `rx 0`, no `RxOK`. See *First run on the board* below. QEMU has no RTL8168 model. The
code is `hal/src/rtl8169.rs` (pure, over two seams) and `kernel/src/network/rtl8168.rs` (the adapter: PCI, BAR2, DMA, logs).
The 17 host tests run the driver against a software model of the device in the same file; they prove the driver does what its
author *understood* the chip to need (ring ownership, descriptor write order, padding, FCS, `Cfg9346` locking, PCIDAC), not
that the chip agrees.

## First run on the board

Oracle: Linux's r8169 on the same machine (`hal/fixtures/rtl8168h-linux-regs.bin`, `rtl8168h-lspci.txt`).

Verified against the hardware:
- `XID 0x541` (Linux: `RTL8168h/8111h ... XID 541`), `Rtl8168H` family, MAC `f0:2f:74:c9:80:a7` (Linux's `ip link`), link 1000 Mb/s full
  duplex. BAR2 = `0xf6504000` 4 KiB, as `lspci` says.
- `ChipCmd.Reset` completes, the MAC survives it, auto-negotiation by MDIO alone ends with link up (4 s).
- **Every register the driver writes reads back as written** (TxConfig, RxConfig `0x0002cf0a`, CPlusCmd, ring base addresses,
  ChipCmd `0x0c`, MaxTxPacketSize, RxMaxSize), so the register map and the `Cfg9346` unlock are right.
- `RxConfig` bits (burst, early-off, multi, 128-int) equal Linux's real `0x0002cf0e` apart from the multicast accept bit.

Differences from what Linux leaves, found by diffing the dumps, and fixed: `TxConfig` has `AUTO_FIFO` (0x80) in Linux (the
driver did not set it); `MaxTxPacketSize` is `0x27` in Linux (the driver wrote `0x3b`). Differences left on purpose: Linux
runs interrupt-driven (`IntrMask 0x2f`), keeps a multicast hash in `MAR0`, leaves `CPlusCmd` `0x2060` (RX checksum and VLAN
offload on), `RxMaxSize` `0x4000`; and a few chip-specific registers at `0x80-0x82` and `0xb0-0xbb` (EEE/PHY related) that
the generic path does not touch.

**Second run (after the AUTO_FIFO fix)**: TX works at the chip level (7 DHCP discovers sent, descriptors consumed, `TxOK`), link up, and
**RX saw nothing**: no `RxOK`, no `RxDescUnavail`, `IntrStatus 0`, RX descriptor 0 still owned by the chip. So no frame reached the
MAC. Prime suspect, from Linux's `rtl_hw_start_8168h_1`: the 8168g/h comes out of reset with `MISC.RXDV_GATED_EN` (bit 19 of
`0xf0`) set, which drops every received frame; Linux clears it and also programs FIFO sizes/pause thresholds through ERI. The
driver now does this (`mac_start_8168gh`: ERI `0xc8/0xe8/0xcc/0xd0/0xdc/0x5f0/0xc0/0xb8/0x1b0`, gate open, `DLLPR`/`MISC_1`
power bits) and `/proc/nic` prints `MISC ... (RXDV gate CLOSED|open)`. Still not done from `rtl_hw_start_8168h_1`: EPHY
table, MAC-OCP tuning (`0xd412`, `0xe056`...), `rtl_pcie_state_l2l3_disable`, ASPM entry latency. Next if RX is still 0: those, then
the PHY page-0x0c42 / EEE settings.

**Not known**: whether a DHCP lease arrives. The run showed an empty `/etc/resolv.conf` and failing pings, but the tests were
typed with QEMU's `10.0.2.x` addresses (a real LAN has none) and `$ns` was empty, so it proves nothing about TX/RX. From
now on read `/proc/nic` (below) instead of guessing.

## `/proc/nic`

`cat /proc/nic` on any NIC: how many times the stack was polled, NIC interrupts, the MAC, the DHCP lease (or `none`), and for
the Realtek: rx/tx frame and drop counters, `ChipCmd`/`TxPoll`/`IntrStatus`, TxConfig/RxConfig/CPlusCmd, the ring base
registers, the events the chip raised since init (`RxOK TxOK RxOverflow RxFIFOOver TxErr TxDescUnavail SysErr ...`: `SysErr` =
PCIe/DMA failure), the ring cursors with their descriptors' `opts1`, and the first 24 bytes of the last 8 frames each way.
How to read it: `tx` rising with `rx 0` = frames go out and nothing comes back (look at `events seen`); `tx 0` = the stack
never sent (look at `polled`); `rx` rising but no lease = RX works and the problem is in the stack/DHCP; `tx` stuck with
`tail.opts1` having OWN set = the chip never consumed the TX descriptor.

## Where the constants come from

Linux's `drivers/net/ethernet/realtek/r8169_main.c`, **from memory**: there is no datasheet in the repository. Treat every
register offset, bit and the `XID` table as unverified until a run on the board or an `ethtool -d` dump agrees.

## What is deliberately not done

- The per-chip `rtl_hw_start_8168*` sequences (EPHY, ERI, OCP, CSI writes, FIFO sizes, ASPM/CLKREQ) and the PHY
  firmware/parameter tables Linux applies per `XID`. The generic path: reset, rings, `TxConfig`/`RxConfig`, restart
  auto-negotiation. It may or may not be enough for this revision; the ladder below says where it stops working.
- Interrupts, offloads (checksum, TSO, VLAN), jumbo frames, multicast filtering (only unicast to our MAC + broadcast), WoL,
  power management, link-change handling after boot.

## The ladder (`nic=` in `/mnt/etc/kernel.conf`, or `--kconf` on a metal run)

Default `off`: the NIC is not touched, boot is as before. Each level includes the one before. Every step logs *before* it
touches the device, so a hang names its last step in the log partition (`rtl8168: ...` lines).

| Level | Does | Writes to the device |
|-------|------|----------------------|
| `probe` | sizes BARs, maps BAR2, reads `TxConfig` (XID), the MAC, `PHYstatus`, logs a hex dump of the 256-byte window | nothing (it turns on PCI memory decode only if firmware left it off) |
| `reset` | + `ChipCmd.Reset`, MDIO writes to restart auto-negotiation, waits up to 6 s for link, dumps the window again, re-reads the MAC | the reset and the PHY |
| `net` | + 64-slot TX/RX rings (one 512 KiB DMA arena), TX/RX enable, `RxConfig` (unicast to our MAC + broadcast), the network stack on top (DHCP, sockets) | everything above, and bus mastering |

virtio-net (QEMU) is tried first and always brought up; the Realtek driver only runs when there is no virtio device.

```bash
scripts/metal-run.sh --kconf 'nic=probe' scripts/metal-jobs/nic-probe.sh   # then: scripts/metal-run.sh --collect
scripts/metal-run.sh --kconf 'nic=reset' scripts/metal-jobs/nic-probe.sh
scripts/metal-run.sh --kconf 'nic=net'   scripts/metal-jobs/nic-net.sh     # needs a LAN with DHCP
```

Run them in this order and stop at the first that misbehaves. READ THE SAVED LOG before believing the verdict
(`metal-run.sh`'s rule).

## What to bring back from the first run

From Linux on the same machine (this is the oracle the driver is compared against):

- `dmesg | grep -i r8169` (the line with `XID`), `ethtool -i <iface>`, `ip link` (the MAC), `ethtool <iface>` (speed/duplex).
- `sudo ethtool -d <iface> raw on > rtl-regs.bin` (the 256-byte register window as Linux leaves it) and
  `sudo lspci -vvvnn -s 08:00.0 -xxxx` (full config space with capabilities). These become fixtures like
  `hal/fixtures/ryzen-pci-config.txt`.
- The saved log of each rung (`target/metal/runs/<nonce>/`): the `rtl8168:` lines, especially `XID`, `mac`, `link` and the two
  register dumps.

What each answer tells:

- **probe**: the XID (compare with Linux's), whether the MAC matches `ip link`, whether the register window matches
  `ethtool -d` outside the fields the OS changes, and whether `PHYstatus` already shows link (firmware or Linux may have
  brought it up).
- **reset**: whether the chip resets (`ResetTimeout` otherwise), whether auto-negotiation completes by MDIO alone (no PHY
  parameter table), and whether the MAC survives the reset.
- **net**: whether a DHCP lease arrives (RX and TX both work), then ping, DNS, HTTP.

## Known unknowns (the first things to suspect)

1. **Link**: the PHY may need the per-`XID` parameter writes Linux applies, or power-up (`PHY_POWER`-style writes), before it
   negotiates. Symptom at `reset`: `link ... up: false` after 6 s although the cable is fine.
2. **Reset side effects**: the MAC (or other registers) might not survive `ChipCmd.Reset` on this revision. Symptom: `mac after
   reset` differs from `mac`. The driver does not rewrite the MAC.
3. **TX**: `TxPoll.NPQ` after `ChipCmd.TxEnable`, `MaxTxPacketSize` (`0x3b`) and `TxConfig` are as remembered for the family;
   a wrong value shows as a lease that never arrives with `tx_frames` rising and no RX.
4. **RX**: `RxConfig` early-off/multi bits, the FCS length (the chip leaves the 4-byte FCS in the length; the driver strips
   it), the 2 KiB buffer vs `RxMaxSize`.
5. **64-bit DMA**: `CPlusCmd.PCIDAC` is set only when the arena is above 4 GiB. If the board's IOMMU or the chip's DAC
   handling differ, symptom is DMA that goes nowhere; the arena's bus address is in the log.
6. **ASPM/CLKREQ** are left as firmware set them; Linux turns them off while touching the EPHY. Not touched here.
